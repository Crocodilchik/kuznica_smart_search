# Умный поиск IT-решений для Store.softline.ru

## Что делаем

Прототип принимает запрос на естественном языке, распознаёт опечатки, жаргон и ограничения, ищет товары в каталоге и предлагает альтернативы и сопутствующие позиции. Для утверждений о совместимости система показывает подтверждение из каталога с явным указанием совместимости или из официальной документации вендора. Целевой каталог по плану проекта — около 200 тыс. позиций. Для первой сквозной сборки используем репрезентативный срез, затем индексируем доступную выгрузку.

**Стек MVP** — Python, Pydantic, LangGraph, Qdrant со встроенным BM25, мультиязычная модель эмбеддингов (например, BGE-M3), универсальный асинхронный LLM Client с DeepSeek API или локальным Ollama и Streamlit. Агенты работают как модули одного приложения. Выбранный LLM-провайдер помогает разбирать сложные запросы и извлекать сведения из документов. Поиск, маршрутизация и обязательные проверки выполняются кодом.

## Кто что делает

| Роль | Агенты и модули | Что реализует | Что передаёт команде |
| --- | --- | --- | --- |
| **Разработчик 1 — оркестрация, демо и аналитика** | Supervisor, Analytics, Streamlit | Заводит общие Pydantic-схемы и тестовые заглушки. Собирает граф LangGraph с маршрутами по артикулу, обычным поиском, подбором альтернатив и дополнений. Подключает интерфейс, логирует результаты и собирает сводку по неудачным запросам. | Единая точка входа `run_search`, рабочее демо, сквозные проверки и отчёт по метрикам. |
| **Разработчик 2 — понимание запроса и валидация** | Query Understanding, Validation, общий LLM Client | Нормализует опечатки и жаргон, извлекает намерение, категорию, артикул, ОС, количество и бюджет. Валидирует структурированный ответ выбранного провайдера через Pydantic. Проверяет ограничения, дубликаты, подтверждения рекомендаций и итоговое количество товаров. | `understand`, `validate`, общий `LLMClient` для разработчика 4. |
| **Разработчик 3 — каталог и гибридный поиск** | Search, загрузчик каталога | Проводит EDA выгрузки, приводит товары к общей схеме и загружает их в Qdrant. Делает точный поиск по SKU, BM25 и dense-поиск с фильтрами. Объединяет два ранжированных списка через RRF и отдаёт режимы сравнения для оценки. | Загружаемый индекс, `search`, общий справочник категорий и атрибутов, тестовый срез каталога. |
| **Разработчик 4 — рекомендации и источники** | Recommendation, Research | Ищет аналоги по назначению и характеристикам, дополнения — по функциональной связи с основным товаром. Готовит небольшой набор документов вендоров, ищет в нём подтверждения и связывает их с конкретными товарами и версиями. | `recommend`, `research`, примеры подтверждённых и неподтверждённых связей. |

## Как собрать каждый блок

1. **Разработчик 1** описывает состояние графа через общие модели, подключает модули как узлы и отвечает за итоговый ответ. По точному SKU запускает прямой поиск. По сложному запросу выбирает нужные узлы, при необходимости делает один повторный поиск с расширенными формулировками или большим лимитом кандидатов. Отправляет событие в аналитику после формирования ответа. Сбой аналитики не влияет на выдачу.
2. **Разработчик 2** начинает со словаря жаргона и безопасных правил для чисел, цен и артикулов. Для сложных формулировок через общий `LLMClient` вызывает настроенный провайдер в структурированном режиме. При ошибке модели возвращает результат правил и отмечает неопределённость; автоматического переключения между локальной и облачной моделью нет. Валидатор реализует обычными проверками по данным каталога и переданным доказательствам.
3. **Разработчик 3** формирует `search_text` из названия, производителя, категории, назначения и важных атрибутов. Для BM25 использует встроенный механизм доступной инсталляции Qdrant. Сначала проверяет полнотекстовый индекс со scoring, а при его отсутствии использует доступный встроенный sparse BM25. Точный артикул ищет по отдельному полю `sku`. Кодирует каталог и запросы одной dense-моделью, применяет жёсткие фильтры к обеим поисковым веткам и объединяет выдачу через RRF. Для сложных фильтров вроде цены комплекта делает дополнительную проверку по карточке. [BM25 по полнотекстовому индексу](https://qdrant.tech/documentation/search/text-search/full-text-search/) · [Встроенный sparse BM25](https://qdrant.tech/documentation/inference/inference-bm25/) · [RRF](https://qdrant.tech/documentation/faq/qdrant-fundamentals/)
4. **Разработчик 4** выводит требования к дополнениям из характеристик и документации, затем обращается к `search` за позициями нужной категории. Для MVP заранее загружает несколько официальных страниц или PDF в локальный корпус и извлекает короткие фрагменты с URL и привязкой к модели или версии. Для извлечения предполагаемой связи из переданного фрагмента Research использует общий `LLMClient`. Подтверждение привязывается к исходному тексту. Сопутствующие позиции должны существовать в каталоге. Конкретные SKU-связки выводятся из данных при обработке запроса.

## Контракты агентов

Внутренние интерфейсы — Python-функции с Pydantic-моделями из `contracts.py`. Пустой список означает успешную обработку без совпадений. Таймаут или недоступность зависимости передаётся отдельно через `warnings` и отражается в статусе ответа. Если поиск недоступен и результатов нет, возвращаем `unavailable`. При успешном поиске без подходящих товаров возвращаем `empty`.

| Агент | Вход → выход | Что гарантирует |
| --- | --- | --- |
| **Supervisor** | `async run_search(SearchRequest) → SearchResponse` | Выбирает маршрут, вызывает проверку перед ответом, возвращает карточки, отдельный список рекомендаций и статус. |
| **Query Understanding** | `async understand(SearchRequest, LLMClient) → QuerySpec` | Возвращает исходный и нормализованный запросы, намерение, известные ограничения и вопрос для уточнения при необходимости. Зависит только от общего интерфейса `LLMClient`. |
| **Search** | `search(SearchParams) → SearchResult` | Возвращает ранжированные карточки каталога со стабильными `product_id` и диагностикой. Поддерживает `sku`, `bm25`, `dense`, `hybrid`. |
| **Recommendation** | `recommend(QuerySpec, anchors: list[Product]) → RecommendationResult` | Для каждого кандидата указывает исходный товар, карточку найденного товара, тип связи и основание. Может вызвать Search для поиска дополнений по категории. |
| **Research** | `async research(RecommendationDraft, LLMClient) → EvidenceResult` | Возвращает найденные фрагменты с источниками и статус `confirmed`, `contradicted` или `unknown`. Зависит только от общего интерфейса `LLMClient`. |
| **Validation** | `validate(QuerySpec, SearchResult, RecommendationResult, list[EvidenceResult]) → ValidationResult` | Возвращает проверенные товары и рекомендации, причины отклонения и признак `needs_retry`. Для отключённых веток принимает пустые результаты. |
| **Analytics** | `record(SearchEvent) → None`, `summarize(events) → AnalyticsReport` | Записывает результаты и агрегирует долю пустых выдач, частые проблемные категории и причины отклонения. |

### Общие модели

| Модель | Поля и правила |
| --- | --- |
| `SearchRequest` | `query`, `request_id`, необязательные `session_id` и контекст предыдущего запроса. |
| `QuerySpec` | `raw_query`, `normalized_query`, `intent` ∈ `exact_product / product_search / alternatives / complements / solution`, `sku?`, `category?`, `hard_filters`, `preferences`, `clarifying_question?`. Неизвестные значения — `null` или пустая коллекция. |
| `hard_filters` / `preferences` | Жёсткие фильтры MVP: `os?`, `country?` (код страны), `devices?`, `max_total_price_kopecks?`, `budget_scope?` (`primary` или `bundle`), `in_stock?`. Мягкие пожелания: `preferred_brand?`, `target_price_kopecks?`. Цены передаются целыми числами в копейках, `devices` — положительное целое. |
| `SearchParams` / `SearchResult` | На входе `query_spec`, `mode`, `top_k`. На выходе `hits[]` с `product`, `rank`, `score?` и `warnings[]`. |
| `Product` | `product_id`, `sku?`, `title`, `category`, `brand?`, `price_kopecks?`, `license_units?`, `in_stock?`, `url?`, `attributes`. Цена указана за продаваемую единицу. Карточка формируется из выгрузки каталога. Расчёт по нескольким лицензиям допускается, если известны правила их покупки и комплектации. |
| `RecommendationDraft` / `RecommendationResult` | У кандидата `anchor_id`, `product`, `type` ∈ `substitute / cross_sell / upsell`, `claim`. Результат содержит `recommendations[]` и `warnings[]`. Для MVP обязательны первые два типа. |
| `EvidenceResult` | `anchor_id`, `product_id`, `claim`, `status`, `evidence[]` с полями `source_type`, `source_url?`, `catalog_field?`, `excerpt`, `checked_at`. Для документа вендора обязателен URL, для данных каталога — поле карточки. |
| `ValidationResult` / `SearchResponse` | Общие поля `products[]`, `recommendations[]` с подтверждениями и `warnings[]`. У проверки есть `needs_retry` и коды отклонений. У ответа — `request_id`, `status` ∈ `ok / partial / empty / clarification_needed / unavailable` и `clarifying_question?`. |
| `SearchEvent` | `request_id`, `normalized_query`, `intent`, `status`, `result_count`, `latency_ms`, `retry_count`, `reason_codes[]`. |

**Правило выдачи.** Для подборочного запроса показываем минимум четыре уникальных подходящих товара, если поиск и проверка нашли достаточно позиций. При нехватке один раз расширяем поиск, сохраняя жёсткие ограничения, затем объединяем результаты по `product_id` и повторяем проверку. Если подходящих товаров всё равно меньше четырёх, показываем найденное со статусом `partial` или `empty` и пояснением. Точный запрос по SKU может вернуть одну карточку. Сопутствующие позиции показываем отдельно. Бюджет основного товара применяем к подбору основного товара и его замен. Бюджет всего комплекта проверяем по сумме, когда пользователь явно задал его для комплекта. Утверждение о технической совместимости публикуем только при наличии подтверждения для нужных модели и версии.

**Пример обмена.** «Российский антивирь для винды на 50 компов до 100к» → `intent=product_search`, `category=endpoint_security`, `os=Windows`, `country=RU`, `devices=50`, `max_total_price_kopecks=10000000`. Поиск применяет доступные фильтры. Validation проверяет стоимость лицензирования 50 устройств по данным каталога. При неизвестной стоимости или ёмкости лицензии позиция не считается подтверждённым попаданием в бюджет.

## Порядок интеграции

1. Разработчик 1 фиксирует схемы и раздаёт заглушки. Разработчик 3 передаёт тестовый срез и список категорий. Остальные разрабатывают свои модули на тех же примерах входа и выхода.
2. Собираем сквозной маршрут **запрос → понимание → поиск → проверка → карточки**. Затем добавляем рекомендации, документы вендоров, один повторный поиск и журнал.
3. К демо проверяем точный SKU, жаргон и опечатку, ограничение по суммарному бюджету, запрос на альтернативы, подтверждённое дополнение и сценарий с менее чем четырьмя результатами. Добавляем проверку на недоступность выбранного LLM-провайдера.
4. На одной размеченной выборке сравниваем **BM25 → dense → hybrid → агентский hybrid**. Разработчик 3 готовит режимы запуска, разработчик 1 сводит Precision@4, NDCG@10, долю пустых выдач и P95 задержки. Разработчики 2 и 4 проверяют соблюдение ограничений и корректность подтверждений.

После MVP можно добавить отдельный reranker, автоматическое пополнение корпуса документации, дашборд спроса и граф связей товаров. Состав фильтров и сценариев лицензирования уточняем после EDA реальной выгрузки.
