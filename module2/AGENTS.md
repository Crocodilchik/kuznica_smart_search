# AGENTS.md

## 1. Контекст проекта

Проект Smart Search разрабатывается для хакатона «ИИкузница», трек «Аналитик данных», кейс Софтлайн «Умный поиск на сайте». Целевой пользователь — клиент Store.softline.ru. Дата защиты прототипа — 2 декабря 2026 года.

Текущий поиск недостаточно хорошо понимает смысл запросов, опечатки, профессиональный жаргон и контекст. Например, запрос «сервер» может возвращать ПО для установки на сервер вместо серверного оборудования. Бизнес-цель — повысить релевантность выдачи и создать инструмент допродаж через рекомендации связанных решений.

## 2. Требования и ограничения

- Каталог заказчика насчитывает около 200 000 товаров; ориентировочная нагрузка — 500 поисковых обращений в день.
- Организаторы предоставляют каталог и выборку поисковых запросов; также доступны сайт магазина и открытые источники, прежде всего сайты вендоров.
- Готовые ручные связи между товарами и интеграции с API не предоставляются.
- Поиск должен понимать смысл, опечатки, синонимы и профессиональный сленг.
- Ответ должен содержать минимум четыре товара. Если каталог объективно не содержит достаточно релевантных позиций, расширять поиск и явно обозначать альтернативы; не выдумывать товары и не скрывать нехватку результатов.
- Рекомендации должны опираться на каталог и проверенные внешние источники.
- Подсказки при вводе — бонусный функционал; акции и сравнение цен — возможные дополнительные сценарии.
- Масштабируемость и готовность к промышленному размещению на витрине не обязательны.

Источник требований: презентация заказчика «ИИкузница — Умный поиск на сайте», страницы 2–5. Форматы и состав полей датасетов пока не подтверждены.

## 3. Целевой результат

Работающий автономный прототип интеллектуального товарного поиска: поисковый модуль, рекомендательная система, REST API, демонстрационный веб-интерфейс и воспроизводимая оценка качества. Не требуется разрабатывать полноценный интернет-магазин или интегрировать решение с действующей витриной.

## 4. Предлагаемая архитектура

Модульный монолит на Python с отдельным интерфейсом. Архитектура и стек ниже — предварительные инженерные решения команды, а не обязательные требования заказчика. Уточнять их после изучения репозитория, данных и доступных ресурсов.

- Python, FastAPI, Pydantic — backend и контракты.
- Pandas или Polars — обработка данных.
- Qdrant — векторный и, при выбранной реализации, разреженный поисковый индекс.
- PostgreSQL либо более простое локальное хранилище для прототипа — каталог, связи и метаданные.
- BM25 и многоязычные embeddings (кандидат: BGE-M3) — гибридный поиск.
- Cross-encoder reranker (кандидат: BGE-reranker-v2-m3) — дополнительное ранжирование при наличии ресурсов.
- RapidFuzz, словарь синонимов, опционально LLM — нормализация и интерпретация запросов.
- Streamlit или React — демонстрационный интерфейс; предпочтителен вариант с меньшими затратами времени.
- Docker Compose — воспроизводимый локальный запуск, если нужен.

Не вводить отдельный микросервис для каждого модуля, агентный фреймворк или сложную инфраструктуру без обоснованной необходимости.

## 5. Пайплайны

### Offline: подготовка данных

1. Загрузить исходный каталог и выборку запросов, исследовать схему, пропуски, дубликаты, категории и распределения.
2. Нормализовать товары, сохранить стабильные идентификаторы и исходные значения; подготовить текстовые представления для поиска.
3. Обогатить данные сведениями вендоров там, где это необходимо и возможно; сохранять URL источника и дату получения.
4. Построить полнотекстовый и векторный индексы; не пересчитывать embeddings на каждый пользовательский запрос.
5. Сформировать связи между товарами: аналоги, сопутствующие решения и подтвержденная совместимость. Не подменять совместимость текстовой близостью.
6. Сохранить обработанный каталог, индексы, связи и метаданные; подготовить отдельную тестовую выборку запросов.

### Online: обработка запроса

1. Получить исходный запрос через API или интерфейс.
2. Нормализовать запрос, распознать жаргон, опечатки, намерение, категории и явно заданные ограничения. Сохранять исходный запрос; не искажать артикулы и названия моделей.
3. Выполнить полнотекстовый и семантический поиск. Начальная гипотеза — до 50 кандидатов от каждого метода; параметры настраиваются по результатам оценки.
4. Объединить и дедуплицировать кандидатов (например, Reciprocal Rank Fusion).
5. Выполнить повторное ранжирование и проверку ограничений, сохраняя точные совпадения по SKU и модели. Не вводить жесткий фильтр по категории при неоднозначном намерении без основания.
6. Подобрать аналоги и сопутствующие решения на основе подтвержденных связей.
7. Сформировать выдачу: минимум четыре товара при наличии подходящих позиций, отдельные рекомендации, обоснования и ссылки на источники там, где это применимо.
8. Отобразить результат и зарегистрировать технические метрики обработки.

Пример сценария: «антивирь для сервака на астре» → «антивирус для сервера под управлением Astra Linux» → поиск ПО безопасности → проверка совместимости → ранжированная выдача.

## 6. Команда и границы ответственности

| Роль | Зона ответственности | Результат |
| --- | --- | --- |
| 1. Data Engineer | EDA, ETL, очистка каталога, получение и подготовка внешних данных | Структурированный каталог и данные источников |
| 2. ML / Search Engineer | Индексация, BM25, embeddings, гибридный поиск, reranking | Поисковое ядро и ранжированные кандидаты |
| 3. AI / Recommendation Engineer | Анализ запросов, синонимы, намерения, формирование связей и рекомендаций | Анализатор запросов и рекомендательный модуль |
| 4. Backend Engineer / Tech Lead | Архитектура, контракты, API, оркестрация, запуск, интеграционные тесты | Интегрированный backend |
| 5. Frontend Developer / Data Analyst | Демонстрационный интерфейс, тестовая выборка совместно с командой, метрики и визуализация | UI и отчет об эффективности |

Разметка тестовых запросов — совместная задача; методика оценки и итоговый отчет закреплены за участником 5. Конкретное распределение по людям еще не подтверждено. Не предполагать, что агенту поручена определенная роль, если пользователь явно не указал ее.

## 8. Контракты взаимодействия

До независимой реализации модулей согласовать общие схемы. Предварительные сущности:

- `Product`: стабильный ID, название, описание, категория, бренд, артикул, характеристики, цена, URL — при наличии этих полей в данных.
- `SearchQuery`: исходный запрос, нормализованный запрос, намерение, ограничения, лимит выдачи.
- `SearchHit`: ID товара, позиция, оценка релевантности и доступные метаданные.
- `Recommendation`: ID рекомендуемого товара, тип связи, обоснование, источники и степень подтверждения.
- `SearchResponse`: результаты поиска, отдельные рекомендации и метаданные ответа.

Предварительные API endpoints: `POST /api/search`, `GET /api/recommendations/{id}`, опционально `GET /api/suggestions`, `POST /api/events`, `GET /api/analytics`. Не считать эти контракты окончательными без согласования с командой. Для параллельной разработки использовать небольшие тестовые фикстуры и моки с одинаковыми схемами.

## 9. Оценка качества

Сравнить baseline (обычный текстовый поиск), семантический поиск и предлагаемый гибридный поиск на одинаковой размеченной выборке. Использовать Precision@4, NDCG@4, долю запросов без результатов и задержку ответа (например, p50/p95). Проверить запросы с опечатками, сленгом, точными артикулами, неоднозначным смыслом и ограничениями совместимости.

Не использовать тестовую выборку для настройки алгоритма; при необходимости выделить отдельную validation-выборку. Не заявлять рост конверсии или выручки без соответствующих данных и экспериментов. Не называть рекомендации «часто покупают вместе», если история покупок этого не подтверждает.

## 10. Приоритеты и план

MVP: обработанный каталог, поиск по смыслу и словам, обработка опечаток и сленга, выдача товаров, обоснованные рекомендации, простой интерфейс, оценка качества. Дополнительно: подсказки, акции, сравнение цен, расширенный дашборд.

Предварительный график: 26 ноября — исследование и контракты; 27–28 ноября — подготовка каталога и поиск; 29 ноября — рекомендации; 30 ноября — интеграция; 1 декабря — тестирование и презентация; 2 декабря — защита.

## 11. Правила работы агента

- Перед изменениями изучить существующий код, README, зависимости, тесты и доступные данные. Не считать предложенный стек уже установленным.
- Работать в рамках поставленной задачи и зоны ответственности; не переписывать соседние модули без необходимости.
- При изменении общих контрактов явно указать затронутые компоненты и согласовать несовместимые изменения.
- Не выдумывать структуру входных файлов, товары, цены, акции, результаты тестов, внешние источники или совместимость. Отмечать неизвестное и отделять тестовые данные от реальных.
- Не отправлять полный каталог или историю запросов во внешние LLM API без подтверждения допустимости передачи данных. Не хранить секреты в коде; использовать переменные окружения и `.env.example` без реальных ключей.
- Предпочитать простые, тестируемые решения; не усложнять проект ради архитектуры. Учитывать ограничения CPU, GPU, памяти и времени на индексацию.
- Добавлять или обновлять тесты для изменяемого поведения. Проверять корректность результата и сообщать, какие проверки фактически выполнены и какие не удалось выполнить.
- Не добавлять крупные датасеты, модели, индексы и секреты в Git. Сохранять инструкции для их воспроизводимой подготовки.
- Обновлять README при изменении способов запуска и контрактов; документировать существенные решения и ограничения.
- Не выполнять необратимые операции, не удалять исходные данные и не затирать изменения других участников без явного разрешения.
- В итоговом сообщении кратко перечислять изменения, затронутые файлы, результаты проверок и оставшиеся блокеры.

## 12. Открытые вопросы

Формат и поля фактических датасетов, наличие кликов и покупок, эталонная выдача, доступные вычислительные ресурсы, допустимость облачных LLM, требования к охвату каталога, критерии оценки жюри и формат сдачи требуют уточнения. До получения ответов принимать минимальные обратимые решения и явно фиксировать допущения.
