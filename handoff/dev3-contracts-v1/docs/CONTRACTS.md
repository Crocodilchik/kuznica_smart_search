# Контракты и данные для разработчиков 1, 2 и 4

Этот документ описывает **фактически реализованные** интерфейсы блока разработчика 3.
Версия пакета: `dev3-contracts-v1`. Источник истины — [Pydantic-модели](../softline_search/contracts.py)
и сгенерированные [JSON Schema](../schemas/). Дополнительные поля моделей запрещены (`extra=forbid`).
Транспорт сейчас — Python-функции с JSON-совместимыми объектами; HTTP-сервер и REST-маршруты не вводятся.

Готовый пакет создаёт `python tools/build_team_handoff.py`: каталог `handoff/dev3-contracts-v1`
и архив `handoff/dev3-contracts-v1.zip`.

## Кто кому что передаёт

| Отправитель → получатель | Объект | Назначение |
| --- | --- | --- |
| Разработчик 2 → оркестратор / поиск | `QuerySpec` | Разобранный запрос и ограничения |
| Разработчик 1 → поиск | `SearchParams` | `query_spec`, выбранный `mode`, `top_k` |
| Поиск → разработчики 1 и 2 | `SearchResult` | Найденные карточки, ранги, оценки и диагностика |
| Оркестратор → разработчик 4 | `QuerySpec` и `anchors: list[Product]` | Исходная потребность и основные товары |
| Разработчик 4 → поиск | `SearchParams` | Поиск кандидатов в альтернативы или дополнения |
| Каталог → разработчики 2 и 4 | `Product`, справочники, срез | Проверка ограничений и формирование рекомендаций |

В примере `recommendation_input_server.json` эти два аргумента собраны в объект
`{"query_spec": ..., "anchors": [...]}` для удобства передачи. Это форма примера;
функцию `recommend(query_spec, anchors)` реализует разработчик 4.

## Разработчик 2: обязательный вход QuerySpec

Полный пример находится в `examples/dev2_query_spec_inventory.json` пакета.
Он содержит исходный запрос: «Нужно ПО для инвентаризации 50 ПК под Windows в наличии до 100 тысяч рублей».

| Поле | Тип | Правило |
| --- | --- | --- |
| `raw_query` | string, обязательно | Исходный пользовательский текст |
| `normalized_query` | string, обязательно | Поисковая формулировка с сохранением названий, моделей и версий |
| `intent` | enum | `exact_product`, `product_search`, `alternatives`, `complements`, `solution`; по умолчанию `product_search` |
| `sku` | string или null | Только явно известный артикул; ID предложения не является артикулом |
| `category` | string или null | ID, точное название, полный путь с ` > ` или alias из справочника |
| `hard_filters` | object | Только явно заданные обязательные условия |
| `preferences` | object | Мягкие пожелания; сейчас не меняют ранжирование BM25 |
| `clarifying_question` | string или null | Вопрос для оркестратора при неоднозначности |

### Поля hard_filters

| Поле | Тип | Семантика |
| --- | --- | --- |
| `os` | string или null | Канонические значения из текущего парсера: `Windows`, `Linux`, `macOS`, `Android`, `iOS` |
| `country` | string или null | Двухбуквенный код страны, например `RU`; страна не определяется по языку или названию бренда |
| `devices` | integer > 0 или null | Требуемое число устройств; текущий поиск допускает только подтверждённый пакет нужной ёмкости типа `device` |
| `max_total_price_kopecks` | integer >= 0 или null | Предельная стоимость в копейках; 100 000 ₽ = `10000000` |
| `budget_scope` | `primary`, `bundle` или null | Основной товар либо весь комплект; сумма комплекта проверяется в Validation |
| `in_stock` | boolean или null | `true` — в наличии, `false` — вне наличия, `null` — не ограничивать |

Поля `preferences`: `preferred_brand: string|null`, `target_price_kopecks: integer>=0|null`.

Правила заполнения:

1. Неизвестные условия — `null`; неизвестные коллекции — пустые коллекции. Не использовать пустую строку вместо отсутствия фильтра.
2. Не устанавливать `in_stock=true`, страну или бюджет, если пользователь этого не задавал.
3. Передавать числа JSON-числами. Для `devices` и денежных сумм строки, дроби и boolean недопустимы.
4. Не называть бюджет `max_price`, а категорию `category_id`: входные поля называются ровно как в таблицах.
5. Не добавлять `request_id`, `session_id`, `confidence` и историю чата внутрь QuerySpec или SearchParams.
   Эти сведения хранит оркестратор отдельно.
6. Если явно заданное ограничение не представлено текущим контрактом, запросить уточнение или согласовать расширение
   с разработчиком 1. Не объявлять такое ограничение выполненным и не удалять его молча.
7. `clarifying_question` передаётся оркестратору: поисковая функция сама не останавливает обработку из-за этого поля.

**Особенность текущего фида:** явная страна происхождения отсутствует у всех товаров.
Запрос с `country="RU"` возвращает `empty` и `country_unknown_in_catalog`.
Это не означает, что в магазине нет российских товаров. Если пользователь потребовал отечественное ПО,
нельзя менять `RU` на `null` ради непустой выдачи: требуется обогащение данных/уточнение сценария.
В пакете есть отдельные пример и фактический ответ для этого случая.

## Разработчик 1: SearchParams и SearchResult

### Вызов поиска

Обёртка: `{"query_spec": <QuerySpec>, "mode": "bm25", "top_k": 10}`.

- `mode`: `sku`, `bm25`, `dense`, `hybrid`; по умолчанию `bm25`.
- `top_k`: целое от 1 до 1000; по умолчанию 10.
- `intent` сам по себе не переключает режим. Режим выбирает оркестратор.
- Для точного артикула использовать `mode="sku"` и `query_spec.sku`.
- Поддержанные сейчас режимы без дополнительных весов: `sku`, `bm25`.
- `dense` без модели возвращает `unavailable`; `hybrid` при одной работающей ветке — `partial` с предупреждением.

```python
from softline_search.contracts import QuerySpec, SearchParams
from softline_search.search import SearchEngine

query_spec = QuerySpec.model_validate(developer_2_json)
params = SearchParams(query_spec=query_spec, mode="bm25", top_k=10)

# Один общий экземпляр на процесс: переиспользовать между запросами и агентами.
with SearchEngine("data/catalog", "data/qdrant") as engine:
    result = engine.search(params)
    output_json = result.model_dump(mode="json")
    anchors = [hit.product for hit in result.hits[:4]]
    product = engine.catalog.get_product("49033")
```

`search(params)` из `softline_search.search` — удобная функция с кешируемым экземпляром.
Не создавать конкурентные процессы с одним local-хранилищем Qdrant; для этого нужен серверный режим.

### Поля результата

| Поле | Содержание |
| --- | --- |
| `hits[]` | Объекты с `product`, `rank`, `score`, `branch_scores` |
| `rank` | Позиция начиная с 1 |
| `score` | Оценка соответствующего алгоритма; **не вероятность и не процент уверенности** |
| `branch_scores` | Оценки отдельных веток для hybrid; в обычном BM25 может быть `{}` |
| `warnings[]` | Строки с ограничениями или диагностикой; некоторые содержат пояснение после `:` |
| `status` | `ok`, `empty`, `partial`, `unavailable` |
| `diagnostics` | Режим, backend, дата источника, задержка и сведения об индексе |

Статусы:

- `ok`: поиск выполнен, есть результаты. Не гарантирует четыре карточки, совместимость или валидность всего комплекта.
- `empty`: при успешно применённых условиях совпадений нет либо не разрешилась категория/неизвестна страна во всём фиде.
- `partial`: выполнена не вся запрошенная конфигурация, например отработал BM25 при недоступном dense.
- `unavailable`: зависимость или нужный режим недоступны.

Некорректный вход даёт Pydantic ValidationError и не подменяется пустой выдачей.
Минимум четыре результата, повторный поиск, выбор альтернатив и итоговый SearchResponse — ответственность Supervisor/Validation.

Диагностические обозначения, которые полезно обработать: `category_unresolved`, `country_unknown_in_catalog`,
`query_has_no_search_terms`, `bundle_total_requires_validation`, `index_contains_catalog_subset`,
`dense_not_configured`, `catalog_index_source_mismatch`, `catalog_index_content_mismatch`, `index_not_built`.
Часть кодов находится внутри строк вида `search_unavailable: ...` или `dense_unavailable: ...`.

В `examples/` находятся фактические результаты BM25 и SKU, пустая выдача по стране и
контролируемый пример отсутствующего индекса. Значения задержки относятся только к записи этих примеров.

## Разработчик 4: карточка Product

Карточки `product_software.json`, `product_antivirus.json`, `product_server.json`, `product_unknown.json`
взяты из реального каталога и сериализованы полностью, без сокращений.

| Группа | Поля и смысл |
| --- | --- |
| Идентификация | `product_id` — строковый ID offer; `sku` — артикул или null; `family_id`, `family_name` — семейство |
| Описание | `title`, `brand`, `description`, `url` — сведения из каталога; URL может вести на магазин, а не на документацию вендора |
| Категории | `category` — название; `category_id` — ID; `category_ids` — предки и категория; `category_path` — их названия |
| Цена | `price_kopecks` — положительное целое или null; цена за продаваемую единицу; `source_currency` — исходная валюта |
| Лицензирование | `license_units`, `license_unit_type` (`device`, `user`, `license` или null), `min_purchase`, `license_type` |
| Фильтрация | `os` — массив, `country` — код/null, `in_stock` — true/false/null, `product_type` — software/hardware/unknown |
| Атрибуты | `attributes` — значимые исходные параметры как списки и служебные сведения об их извлечении |
| Происхождение | `source_date`, `data_warnings`, `attributes.price_source`, `attributes.license_units_source` при наличии |
| Поисковое представление | `search_text` — название, бренд, категория, описание и атрибуты; это не подтверждение совместимости |

Верхние поля Product имеют фиксированную схему. Внутри `attributes` ключи динамические:

```json
{
  "Тип лицензии": ["Полная версия"],
  "Срок действия": ["бессрочная"],
  "description_fields": {
    "Платформа": "Windows",
    "Минимальная покупка": "от 1 шт."
  },
  "price_status": "known",
  "price_source": "offer.price",
  "license_units_source": "offer.name"
}
```

Правила работы с карточками:

1. Не изменять `product_id`, не создавать несуществующие SKU и товары. Финальный покупаемый товар обязан быть в каталоге.
2. `family_id` не доказывает взаимозаменяемость: одно семейство включает разные сроки, редакции, продления и типы организаций.
3. `license_type` различает новую лицензию, подписку, продление, поддержку и обновление. Их нельзя автоматически считать аналогами.
4. `license_units=100` имеет смысл только вместе с `license_unit_type`; пользователи/ядра/общие лицензии не равны устройствам.
5. `min_purchase=null` означает неизвестную минимальную покупку. Возможность купить N лицензий по линейной цене не предполагается.
6. Нулевая исходная цена преобразована в `price_kopecks=null`, а не в бесплатный продукт.
7. `available` и цена относятся к дате снимка; `source_date` не является временем проверки сайта вендора.
8. Наличие ОС в списке не подтверждает совместимость двух конкретных продуктов и их версий.
9. Для подтверждения рекомендаций ссылаться на конкретное поле карточки или официальную документацию;
   владелец Research/Evidence — разработчик 4, проверку выполняет разработчик 2.

### Поиск дополнений

Разработчик 4 вызывает тот же SearchParams. В примере `search_params_complements_ups.json`
показан запрос в категорию `ups`. Это получение кандидатов, а не проверенное сочетание с сервером.

Не переносить механически фильтры основного товара на дополнение: ОС сервера не является ОС ИБП,
а количество защищаемых ПК не является ёмкостью лицензии ИБП. Бюджет `primary` относится к основному товару;
бюджет `bundle` требует проверки суммы всего набора, а не только отдельных карточек.

## Общие справочники и примеры

В пакете `data/catalog/`:

- `categories.json`: полное дерево из 9 311 категорий; поля `id`, `name`, `parent_id`, `path_ids`, `path`, `offer_count`.
  `offer_count` — число прямых предложений категории, не сумма всего поддерева.
- `category_aliases.json`: соответствия canonical alias → исходные ID категорий.
- `attributes.json`: количество значений, число уникальных значений, наиболее частые значения.
  `occurrences` считает значения, а не число товаров: у одного товара параметр может повторяться.
- `sample_products.jsonl`: 300 карточек, по одному JSON-объекту на строку; набор воспроизводимый и покрывает разные верхние категории.
- `manifest.json`: размер каталога, качество и хеши источника/нормализованного содержимого.

Aliases: `endpoint_security`, `security`, `server_hardware`, `server_os`, `operating_systems`,
`backup`, `virtualization`, `ups`. Они построены по названиям категорий и требуют проверки на сценариях команды.
Полный справочник категорий содержит необходимые реальные ID; нельзя придумывать новые alias.

## Что входит в архив и что нужно для запуска

Архив содержит исходный код блока, зависимости, JSON Schema, договорённости, примеры и небольшой набор данных.
Он пригоден для интеграции и работы с тестовыми карточками. Тестовый срез не равен полному поисковому индексу.

Для запуска поиска по всем 136 040 предложениям отдельно нужны:

1. Полный `data/catalog/catalog.sqlite` и справочники/manifest той же сборки.
2. `data/qdrant/index.json` и активное хранилище из его `storage_path`.
3. Окружение из `requirements.lock.txt` и установленный Python-пакет проекта.

Для воспроизведения с нуля нужны исходный XML и команды `prepare`, `index` из инструкции интеграции/README проекта.
Большой XML, полный SQLite, Qdrant-хранилище и `.venv` в этот компактный архив не включены.
Нейронные веса и актуальные цены/акции из внешних API не предоставляются.

Не перезаписывать общий contracts.py разработчика 1 вслепую: сравнить схемы и объединить модели.
Разработчик 2 и разработчик 4 не должны объявлять повторно несовместимые версии Product/QuerySpec.
